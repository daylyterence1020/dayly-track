# Harness engineering for AI coding agents (October 2026)

**Scope.** This note synthesizes first-party engineering reports and documentation available by 30 October 2026. “Emerging consensus” below means recurring practices across those sources, not an industry standard. The maturity ladder is my synthesis, not a published framework.

## Definition and boundary

An **agent harness** in the narrow platform sense is the loop that calls a model, supplies context, routes tool calls, and maintains a session; its sandbox is the execution environment. OpenAI describes the Codex harness as the agent loop and logic behind its products; Anthropic separates session, harness, and sandbox. In the broader **harness engineering** sense used by coding-agent teams, the object of engineering also includes the repository-local instructions, executable tools, constraints, and feedback signals that make an existing coding agent productive on a particular codebase. Birgitta Böckeler calls this the user’s “outer harness” and frames it as guides that steer work plus sensors that help the agent correct it. [OpenAI, *Unlocking the Codex harness*](https://openai.com/index/unlocking-the-codex-harness/); [Anthropic, *Scaling Managed Agents*](https://www.anthropic.com/research/managed-agents); [Böckeler, *Harness engineering for coding agent users*](https://martinfowler.com/articles/harness-engineering.html).

The practical aim is to move human effort from repeating instructions and catching routine errors toward specifying intent, exposing relevant evidence, and improving the system after failures. This does **not** imply fully autonomous development is generally solved: OpenAI explicitly cautions that its end-to-end feature workflow depends on substantial repository-specific investment, and Böckeler says functional behavior remains much harder to verify than maintainability or structural rules. [OpenAI, *Harness engineering*](https://openai.com/index/harness-engineering/); [Böckeler, *Harness engineering for coding agent users*](https://martinfowler.com/articles/harness-engineering.html).

## What the harness covers

| Area | Emerging practice and strength of evidence |
| --- | --- |
| Language and stack | **No universal agent-first language winner.** Prefer a stack the team can run and validate reliably. Strong typing provides a useful automatic check; mature, stable, composable libraries and familiar frameworks can make code easier for agents to reason about. These are reasons to consider a language, not a mandate to choose one. GitHub recommends recording exact versions and dependencies in agent instructions. [Böckeler](https://martinfowler.com/articles/harness-engineering.html); [OpenAI](https://openai.com/index/harness-engineering/); [GitHub](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/). |
| Folders and naming | Give agents a concise map of the repo, domain boundaries, key paths, and naming rules. OpenAI uses a short `AGENTS.md` as a table of contents for indexed `docs/`, then enforces schema/type naming and dependency directions with custom linters and structural tests. GitHub recommends concrete project structure, commands, examples, and boundaries; its Copilot instructions can be scoped by file glob. There is no source-backed universal folder tree or naming scheme. [OpenAI](https://openai.com/index/harness-engineering/); [GitHub guide](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/); [GitHub onboarding](https://github.blog/ai-and-ml/github-copilot/onboarding-your-ai-peer-programmer-setting-up-github-copilot-coding-agent-for-success/). |
| Work planning and continuity | Break long work into verifiable increments, preserve the current goal and decisions in versioned artifacts, and leave a clean state for the next session. Anthropic’s long-running experiment used an initializer, feature list, progress file, git history, and an agent that implemented one feature at a time. OpenAI uses lightweight plans for small changes and checked-in execution plans with progress and decision logs for complex ones. [Anthropic, *Effective harnesses*](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [OpenAI](https://openai.com/index/harness-engineering/). |
| Feedback and verification | Put fast deterministic checks close to edits: formatting, types, lint, tests, architectural constraints. Add realistic end-to-end checks, runtime logs/metrics, and agent review where they give new evidence. Human review remains important for ambiguous intent and subjective tradeoffs. OpenAI made the UI and per-worktree logs/metrics accessible to Codex; Anthropic found browser-driven verification useful; Böckeler distinguishes computational from inferential sensors. [OpenAI](https://openai.com/index/harness-engineering/); [Anthropic, *Effective harnesses*](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [Böckeler](https://martinfowler.com/articles/harness-engineering.html). |
| Automation and autonomy | Automate repeatable, bounded tasks with explicit triggers, permissions, allowed outputs, and escalation points. GitHub Agentic Workflows defines triggers, permissions, and safe outputs in workflow frontmatter. OpenAI reports agents handling bug reproduction through PR and merge in its own highly instrumented repo, with humans escalating judgment calls. Agent teams are an available pattern, not a settled default: Anthropic’s 2025 report called single versus multi-agent design an open question, and its 2026 work finds additional evaluators useful for some demanding tasks but costly. [GitHub Docs](https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows); [OpenAI](https://openai.com/index/harness-engineering/); [Anthropic 2025](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [Anthropic 2026](https://www.anthropic.com/research/harness-design-long-running-apps). |
| Library use | Favor dependencies whose API, behavior, and version are clear to the agent and whose outputs can be validated. OpenAI favors stable, composable technologies and sometimes implements a small subset in-repo when an upstream package is opaque, but also states a principle of shared utilities over proliferating hand-rolled helpers. Thus, “never use libraries” and “always use libraries” both overstate the evidence; decide by inspectability, maintenance cost, and tests. [OpenAI](https://openai.com/index/harness-engineering/). |

## Additional areas that materially affect results

1. **Context architecture and freshness.** A short entry point should lead to authoritative, indexed, versioned documentation. OpenAI found a huge `AGENTS.md` consumed context and decayed; it uses CI and a recurring documentation agent to check links, structure, and staleness. This is more than prompt wording: it determines which facts the agent can discover at the moment of work. [OpenAI](https://openai.com/index/harness-engineering/).
2. **Architecture as executable constraints.** Documented layering alone is weak. OpenAI validates dependency directions, file size, logging, naming, and reliability requirements mechanically; custom error messages tell the agent how to repair violations. Böckeler distinguishes this architecture-fitness harness from basic maintainability checks. [OpenAI](https://openai.com/index/harness-engineering/); [Böckeler](https://martinfowler.com/articles/harness-engineering.html).
3. **Environment and tool access.** Reproducible setup, working build commands, an isolated workspace, and access to the same tools as developers determine whether an agent can actually verify its work. GitHub describes setting up Copilot’s container with project services and tools; OpenAI runs app instances and observability per worktree. [GitHub onboarding](https://github.blog/ai-and-ml/github-copilot/onboarding-your-ai-peer-programmer-setting-up-github-copilot-coding-agent-for-success/); [OpenAI](https://openai.com/index/harness-engineering/).
4. **Safety and authority boundaries.** Give agents the least access needed for each job, including file scopes and allowed write operations. GitHub’s guidance names explicit do/ask/never boundaries for custom agents, and its scheduled workflows declare permissions and safe outputs. This is an operating design choice, not only a security policy. [GitHub guide](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/); [GitHub Docs](https://docs.github.com/en/copilot/how-tos/github-agentic-workflows/creating-github-agentic-workflows).
5. **Harness evaluation and upkeep.** Google recommends observable behavioral evals (for example, whether an agent runs a validator after changing a build file) to diagnose prompt/tool/model regressions, alongside end-to-end scores. Anthropic recommends testing harness parts against realistic traces and removing scaffolding that a newer model no longer needs. OpenAI treats repeated code drift as a prompt for recurring cleanup rules and automation. [Google, *Anatomy of Harness Engineering*](https://developers.googleblog.com/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/); [Anthropic, *Harness design*](https://www.anthropic.com/research/harness-design-long-running-apps); [OpenAI](https://openai.com/index/harness-engineering/).
6. **Specification quality and independent acceptance evidence.** A passing test suite written by the same agent does not by itself prove that the requested behavior is right. Böckeler identifies behavior harnesses as an open problem; Anthropic’s evaluator improved a complex app but still missed deeper interaction bugs. Acceptance examples, real user journeys, and human judgment remain especially valuable here. [Böckeler](https://martinfowler.com/articles/harness-engineering.html); [Anthropic, *Harness design*](https://www.anthropic.com/research/harness-design-long-running-apps).

## A practical maturity ladder (synthesis)

This ladder is an **inference from the sources**, not a published standard. Advance when repeated failures or wasted review time justify the next layer; Anthropic explicitly warns that harness complexity has costs and should be revisited as models improve. [Anthropic, *Harness design*](https://www.anthropic.com/research/harness-design-long-running-apps).

| Level | What is present | Typical proof of readiness |
| --- | --- | --- |
| 0. Ad hoc | Agent receives a task and can inspect/edit files. | A human must explain setup and manually discover most errors. |
| 1. Reproducible | Working setup and exact build/test commands, concise repo map, stack and boundaries. | A new agent can build and run the project without oral context. |
| 2. Guided and checked | Scoped instructions, example patterns, fast tests/types/lints, explicit acceptance criteria. | Routine errors feed directly back to the agent for correction. |
| 3. Stateful and observable | Versioned plans and decisions, session handoff, browser or API journeys, logs and metrics, structural checks. | An agent can resume long work, reproduce a bug, and show evidence of a fix. |
| 4. Governed automation | Bounded recurring jobs, review loops, permissions, behavioral evals, drift/doc cleanup, human escalation. | Teams can expand autonomy for defined tasks while measuring failure modes and revising the harness. |

This ordering follows the reported progression from setup/instructions (GitHub), to incremental handoff and verification (Anthropic), to repository-level architecture, observability, and recurring cleanup (OpenAI), and finally to explicit harness evals (Google). The stages can overlap and should not be used as a score for code quality. [GitHub onboarding](https://github.blog/ai-and-ml/github-copilot/onboarding-your-ai-peer-programmer-setting-up-github-copilot-coding-agent-for-success/); [Anthropic, *Effective harnesses*](https://www.anthropic.com/research/effective-harnesses-for-long-running-agents); [OpenAI](https://openai.com/index/harness-engineering/); [Google](https://developers.googleblog.com/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/).

## Implications for a new small project

Start with a language and framework that fit the product and offer simple local validation; put exact setup and validation commands, directory responsibilities, and dependency rules in a compact agent entry point. Add one runnable user journey and a small set of deterministic checks before building autonomous workflows. Record major decisions and acceptance criteria in files the agent can find. Add specialized agents, recurring maintenance, or a bespoke evaluation suite when actual failure patterns justify them. This is a synthesis of the practices above, particularly GitHub’s advice to start with one narrow agent and Google’s advice to dogfood before building a complex eval harness. [GitHub guide](https://github.blog/ai-and-ml/github-copilot/how-to-write-a-great-agents-md-lessons-from-over-2500-repositories/); [Google](https://developers.googleblog.com/the-anatomy-of-harness-engineering-how-to-evaluate-iterate-and-guard-ai-coding-agents/); [Anthropic, *Harness design*](https://www.anthropic.com/research/harness-design-long-running-apps).
