# DaylyTrack Coding Agent Harness

## 目的與權威來源

本文件規範 Codex 如何在此專案執行已交辦的開發任務。使用者負責產品規劃、任務目標和產品決策；代理負責按已確認規格實作、驗證及回報。

- `docs/product-spec.md` 是首版資料模型、互動、狀態、封存和驗收規則的唯一產品來源。
- 本文件是 Coding Agent 工作流程、依賴、驗證和交付規則的來源。
- 程式碼、套件設定和 Sites 設定是實際執行方式的來源；文件不取代這些設定。
- 將新增的規則寫在其唯一權威文件中，避免複製同一要求到多處。

## 已確認的試驗技術選型

首版試驗採用 Sites 支援的 **React + Vinext + Cloudflare Workers + D1**：

- React 負責 UI 元件；使用 TypeScript（除非既有專案設定另有決定）。
- Vinext 提供 React 全端框架、路由及建置流程，使用 Sites 提供的起始專案。
- Cloudflare Workers 執行伺服器端程式；遵守 Workers 執行環境及 Sites 託管層的 API、網路和套件相容限制，不假設完整 Node.js 執行環境。
- Cloudflare D1 作為持久關聯式資料庫，使用 SQLite 相容 SQL；不得假設 PostgreSQL 專屬語法或功能可用。
- 依起始專案提供的本機預覽及本機 D1 遷移流程開發及驗證。首版登入使用 DaylyTrack 電郵驗證碼與獨立帳戶 ID；正式 Site 的 D1 不得用於測試。

使用者已確認以此組合作為首版試驗，因此不需再次詢問是否採用上述技術方向。Vinext 與 Sites 能力可能更新；每次新增平台整合或首次使用某項能力前，仍須查閱當前官方文件和起始專案設定，核對實際支援範圍。Vinext 若仍屬 beta，應在任務方案或完成回報中說明此維護風險。

已確認架構不代表所有套件依賴均已核准。引入或升級第三方依賴前，仍依「依賴與專案內 Library」列出用途、版本、維護狀態、Sites 相容性和替代方案，並等待使用者確認。先檢查 Sites 起始專案已有的依賴及可用指令，避免重複安裝或引入未使用套件。

## 接受任務與規劃

使用者提供產品意圖和任務目標。代理應先閱讀 `AGENTS.md`、產品規格及任務實際涉及的程式碼和設定。

- 單一、清楚且範圍有限的工作直接執行，不另寫計劃文件。
- 跨越多個模組、涉及資料模型或多個驗收條件的工作，先列出精簡實作步驟及對應驗收項目，再開始修改。
- 若任務需要改變已確認的資料模型、互動、狀態或驗收規則，先指出產品規格相關段落、衝突及影響，等待使用者決定。其餘不受影響的工作可以繼續。
- 對技術細節可自行作出符合已確認技術選型的實作決定；不得把產品方向或未確認規則當成技術細節自行決定。

## 程式碼、目錄與命名

- 詳細產品規格、架構決策和開發流程放在 `docs/`；程式碼、測試及建置設定留在其各自的程式專案目錄。
- 建立檔案前先檢查現有結構與同類範例，沿用已存在且一致的命名和模組邊界。
- `site/app/` 放頁面、版面及全域樣式；使用 Vinext 的 `page.tsx`、`layout.tsx` 等路由檔案，不另設 `index.html` 或 HTML 模板目錄。
- `site/components/` 放可重用的介面元件；`site/components/ui/` 保留給通用 UI 元件。只供單一頁面或功能使用的元件可放在其使用位置附近。
- `site/public/` 放可由網址直接存取的圖片、Logo 等靜態素材。全域樣式沿用 `site/app/globals.css`；有多份實際共用樣式時才考慮新增樣式目錄。
- `site/db/` 放 D1 的 schema、連線及資料存取程式；`site/drizzle/` 放遷移檔及其紀錄。`site/examples/d1/` 是起始專案範例，不作為正式資料模型的位置。
- `site/scripts/` 放安裝、預覽、建置及 Sites 整合工具；產品的前端互動邏輯放在相關元件或功能模組，共用邏輯才抽到 `site/lib/` 等共用位置。
- 型別優先放在使用它的功能附近；多處共用時才建立共用型別檔案或目錄。隨實際功能增長建立功能目錄，不設籠統的 `others/` 目錄。
- 不為了文件看起來完整而預先建立未使用的目錄、抽象層或工具。

## 依賴與專案內 Library

- 引入或升級任何第三方依賴，包括執行時、開發和測試依賴前，先提出用途、版本、維護狀態、Sites 相容性和替代方案，等待使用者確認。
- 清楚區分執行時依賴與只供本機開發或測試的工具，並說明其會改動的套件設定或開發環境。
- 有多處實際共用需求，或需要集中維護某項規則時，優先評估建立專案內共用模組。單次功能留在其所屬模組。
- 重寫成熟套件的功能前，先說明需要的功能範圍、預期維護成本和已知風險，等待使用者確認。

## 實作與驗證

先找出與變更直接相關的檢查，再按成本由低至高執行。技術選型未確認時，不虛構尚不存在的測試或建置指令；先檢視實際設定。

- 每次變更都要驗證受影響的產品驗收項目及相應程式檢查。
- 首版交付前，依 `docs/product-spec.md` 第 9 節完整核對所有驗收重點。
- 資料模型與狀態轉換使用可重複執行的程式測試；卡片手勢、滑出選項、按鈕、關係網切換和資料保存，使用可行的瀏覽器流程或明確標示限制的人工檢查。
- 手機以觸控滑動、桌面以滑鼠拖拉作為卡片操作；卡片常駐「編輯」按鈕。依產品規格驗證滑出的操作選項和點擊行為，不增設其他常駐操作按鈕。
- 測試只使用隔離的測試資料。不要讓測試讀寫或修改正式 Site 的 D1 資料。
- 完成程式修改後，檢查最終 diff 是否符合任務和產品規格，是否包含不相關檔案、意外資料或敏感內容。
- 所有必要且可執行的檢查均通過後才可建立本機 Git commit。必要檢查失敗或無法執行時，不建立 commit；回報失敗或限制和仍欠缺的證據。
- 若瀏覽器、Sites 或其他驗證工具不可用，清楚標示未驗證部分，不將其描述為通過。

## Sub-agent 委派

預設由單一代理執行。主代理可自行委派能獨立完成且有清楚交付物的研究、程式探索、測試分析或審查工作。

- 主代理保留需求解讀、產品決策、整合、驗收和最終回報責任。
- 委派時說明問題、範圍、預期輸出、是否可修改檔案，以及主代理是否須等待結果。
- 初期不建立專案自訂 sub-agent 角色；先使用 Codex 內建角色。只有在同類任務反覆出現且需要穩定分工時，才提議新增角色。
- 不讓多個代理同時修改相同檔案。若確有並行寫入需要，先使用獨立 Git worktree 並清楚指定整合責任。
- Sub-agent 與主代理共享目前工作環境；角色指示本身不構成獨立檔案或權限隔離。

## Git、外部動作與 Sites

- 代理可建立本機 commit，但須先通過所有必要檢查並完成 diff 自我審查。
- 推送、建立 PR 和正式部署前，必須取得使用者對該外部動作的明確指示。
- Sites 部署屬正式環境操作。只有使用者明確要求部署後，才執行 Sites 的推送、儲存版本及部署流程；完成後確認部署結果。
- 執行 Sites 流程時，依當前 Sites 官方文件和專案中的 `.openai/hosting.json` 操作；不得猜測或另造專案識別碼、權限或部署參數。

## 完成回報

每項任務完成時提供：

1. 變更摘要和受影響檔案。
2. 執行過的檢查、驗收項目及每項結果。
3. 未完成、未通過或無法驗證的工作及原因。
4. 若建立本機 commit，提供其識別資料；若未建立，說明原因。
5. 任何仍待使用者決定的產品、技術或外部操作事項。

## 背景任務

初期不建立排程或無人值守的維護代理。只有當一個維護流程已透過手動執行證明穩定，而且使用者明確要求時，才制定排程；排程內容要限定檢查範圍、允許的檔案變更、外部權限及需要人工介入的條件。
